API overview

The Endors API lets you manage social proof programmatically — create clients and testimonials, upload media, organize folders, build collection links, run AI proof search, and generate pre-call pages — so you can plug Endors into automations, CRM workflows, and MCP agents.

REST JSON Growth plan required

Base URL & envelope

All endpoints are served from your deployment origin over HTTPS. There is no version prefix — paths look like /api/spaces/{spaceId}/testimonials. 

https://app.endors.io

Every authenticated endpoint returns a uniform envelope. On success, data carries the payload; on failure, error carries a stable machine-readable code plus a human-readable message.

Success

json 
{ "ok": true, "data": { "id": "…" } }

Error

json 
{
  "ok": false,
  "error": {
    "code": "PLAN_LIMIT",
    "message": "Testimonial limit reached for this plan."
  }
}
Note

A few media endpoints (assets/upload, video/create-upload, video/status) predate the envelope and return bare objects such as { "assetId": "…" } — this is noted per endpoint.

Field naming conventions

Current Endors API payloads use camelCase for all field names — for example, testimonialId, clientId, createdAt, spaceId. Some older endpoint responses still return snake_case fields inherited from the underlying database (for example, text_content, active_asset, source_created_at, folder_ids), and a few request bodies accept snake_case parameters (for example, text_content on testimonial create and folder_ids=1 on list endpoints). Those snake_case names are legacy: they are documented per-endpoint exactly as the API returns them and will not be silently renamed — changing them would break existing integrations. Any new field added to any endpoint or webhook payload from now on is camelCase. Write your integration against the field names shown in each endpoint's documentation, and do not assume one convention across the whole API.

Authentication

Send your secret API key as a Bearer token. Keys start with sk_live_ and are minted in the dashboard under Settings → API & Webhooks. The raw key is shown exactly once at creation; only a hash and a 16-character prefix are stored. To rotate, delete the key and create a new one. Each space can hold up to 3 keys.

bash 
curl https://app.endors.io/api/spaces/$SPACE_ID/testimonials \
  -H "Authorization: Bearer sk_live_4f9d8c2b7a1e"
js 
const BASE = "https://app.endors.io";
const KEY = process.env.ENDORS_API_KEY;

async function endors(path, options = {}) {
  const res = await fetch(`${BASE}${path}`, {
    ...options,
    headers: {
      Authorization: `Bearer ${KEY}`,
      "Content-Type": "application/json",
      ...options.headers,
    },
  });
  return res.json();
}

const { ok, data } = await endors(
  `/api/spaces/${spaceId}/testimonials?shareLinks=1`
);

Three rules govern API-key calls:

  • One space per key. Every endpoint is scoped by {spaceId} in the path. A key is bound to a single space — requests for any other space's ID return 403.
  • Growth plan required. API access is part of the apiAndWebhooks feature. On lower plans every keyed call returns 403 PLAN_RESTRICTION with an upgrade payload.
  • Full access within the space. A valid key acts with workspace-owner rights inside its space — keep it server-side only, never in client-side code.
Session-only endpoints

A handful of management routes (creating or editing webhooks, managing API keys, embeddings, template editing, data export) accept only an authenticated dashboard session and are not part of the keyed API. Each endpoint page states whether API keys are accepted.

Rate limits

API-key requests to Space-scoped endpoints (/api/spaces/{spaceId}/…) are rate limited per key:

EndpointsLimit
All endpoints (default)120 requests / minute
AI endpoints — POST …/search, POST …/proof/match, POST …/pre-call-pages/generate20 requests / minute

Every response carries the standard headers so well-behaved clients can self-throttle before hitting the limit:

HeaderMeaning
X-RateLimit-LimitThe tier's per-minute limit for this request.
X-RateLimit-RemainingRequests left in the current minute window.
X-RateLimit-ResetUnix epoch seconds when the window resets.
X-Endors-Request-IdA unique id for this request, on every response (including 429s). Include it verbatim when contacting support — it's the anchor we debug from.

Exceeding the limit returns 429 RATE_LIMITED with error.retryAfter (seconds), plus a standard Retry-After header:

json 
{
  "ok": false,
  "error": {
    "code": "RATE_LIMITED",
    "message": "Rate limit exceeded for your API key. Slow down and retry after the window resets.",
    "retryAfter": 37
  }
}
  • The limit is per API key, not per Space — a Space with two keys gets two independent allowances.
  • The window is a fixed 60-second bucket: the first request starts it, and it resets (doesn't slide) 60 seconds later.
  • Session-authenticated dashboard traffic is not subject to these limits.
  • The public collection form and embed endpoints have their own separate limits, unchanged.

Conventions

  • Content type. JSON bodies for every endpoint except the two multipart/raw uploads on the Assets & video page.
  • IDs in the path. Resources are addressed as /api/spaces/{spaceId}/{resource}/{id}; a wrong or foreign id fails with 404 and nothing is written.
  • Fail-fast validation. Create endpoints validate every referenced id (client, asset, folder) before writing anything — a bad reference never leaves a half-created object behind.
  • Streaming endpoints. AI search and Pre-Call pages default to NDJSON streams; both accept a flag (or parameter) that returns the same content as one JSON body for API callers.
  • Idempotency. Creation endpoints accept an Idempotency-Key header: the same key + body returns the original response verbatim; the same key with a different body is 409 IDEMPOTENCY_REPLAY_MISMATCH; a reused in-flight key is 409 IDEMPOTENCY_CONFLICT (retryable — wait for Retry-After). Records are kept for 24 hours. See the Sessions API for the worked example.
  • Pagination. List endpoints support optional keyset pagination: pass limit (positive integer, endpoint-capped) and echo nextCursor back as cursor until a response omits it. Cursor-less requests return the full list exactly as before. Malformed input returns 400 INVALID_LIMIT / 400 INVALID_CURSOR with error.field naming the offending parameter. See the Clients API for the worked example.
  • Webhooks. Everything created through the API fires the same webhooks as the dashboard, with source: "api" where relevant.

Errors

The error.code field is stable and safe to match on; error.message is for humans.

StatusCodeWhen it happens
400BAD_REQUESTMissing required parameters or invalid request body.
400BAD_JSONRequest body is not valid JSON.
400VALIDATION_ERRORPayload failed structural validation (e.g. bulk import rows); rowErrors[] names each failing row.
400LIMIT_REACHEDA per-space limit has been reached (e.g. max API keys).
400CONFIRM_REQUIREDA permanent operation (e.g. custom-field delete) was sent without its confirmation (confirm=true).
400INVALID_LIMITA limit query parameter that isn't a positive integer (paginated list endpoints; error.field names the parameter).
400INVALID_CURSORA cursor query parameter that isn't a valid Endors cursor (paginated list endpoints; error.field names the parameter).
401UNAUTHORIZEDMissing, invalid, or revoked API key.
403FORBIDDENAPI key does not belong to the requested Space.
404NOT_FOUNDThe requested resource does not exist (or belongs to another Space).
409DUPLICATE_FIELDA resource with that name already exists.
403PLAN_RESTRICTIONThe Space's plan does not include this feature (e.g. API access, custom fields, external redirects); response carries a paywall object.
403PLAN_LIMITA plan resource limit is exhausted (e.g. testimonials, embeddings); response carries a paywall object naming the resource and limit.
403SPACE_LOCKEDThe Space is locked (e.g. billing issue) and rejects writes; response carries a paywall object.
403SUBSCRIPTION_REQUIREDAn active subscription is required for this action; response carries a paywall object.
402AI_CREDITS_EXHAUSTEDThe Space is out of AI credits (AI endpoints). Retry with the same request CANNOT succeed — top up credits first; response carries a paywall object with required/available.
429RATE_LIMITEDThe API key exceeded its per-minute rate limit (see rate limits); wait retryAfter seconds and retry (error.retryAfter + Retry-After header).
409IDEMPOTENCY_CONFLICTAn Idempotency-Key was reused while the original request is still in flight; retry shortly with the SAME key and body (Retry-After names the lease TTL).
409IDEMPOTENCY_REPLAY_MISMATCHAn Idempotency-Key was replayed with a DIFFERENT request body — a caller bug; do not retry with this key (send a new key for a new request).
409INVALID_STATEThe requested state transition is not valid from the resource's current state (e.g. cancelling an already-completed session).
500DB_ERRORServer-side database error; contact support.
404CLIENT_NOT_FOUNDThe referenced client does not exist in the Space.
404ASSET_NOT_FOUNDThe referenced asset does not exist in the Space.
404FOLDER_NOT_FOUNDThe referenced folder does not exist in the Space.
422DELIVERY_FAILEDThe delivery retry attempt failed (see the webhook retry policy).

All paywall-carrying errors (PLAN_RESTRICTION, PLAN_LIMIT, SPACE_LOCKED, SUBSCRIPTION_REQUIRED, AI_CREDITS_EXHAUSTED) are part of one paywall family: the response also includes a top-level paywall object your integration can inspect for plan/credit state. AI_CREDITS_EXHAUSTED is the only one at HTTP 402; the rest are 403. RATE_LIMITED is the only retryable 4xx-family code — the SDK (and any well-behaved integration) should honor retryAfter and retry.

Handling errors in code

js 
// Node.js example
const res = await fetch(`https://app.endors.io/api/spaces/${SPACE_ID}/testimonials`, {
  headers: { Authorization: `Bearer ${API_KEY}` }
});

if (!res.ok) {
  const { error } = await res.json();
  console.error(`API error ${res.status}: ${error.code} — ${error.message}`);
}
python 
# Python example
import requests

resp = requests.get(
    f"https://app.endors.io/api/spaces/{SPACE_ID}/testimonials",
    headers={"Authorization": f"Bearer {API_KEY}"}
)

if not resp.ok:
    error = resp.json().get("error", {})
    print(f"API error {resp.status_code}: {error.get('code')} — {error.get('message')}")
    resp.raise_for_status()

Show proof on your website (frontend)

The REST API is for servers (sk_live_ keys — never in browser code). For websites, use the frontend package instead:

bash 
npx endors init

The init command detects your project (Next.js, React, or plain HTML), asks for your embedding id (from Embeds → your wall → Embed id in the dashboard), installs @endors/widgets, and drops in a working example component that mounts the wall:

js 
import { mount } from "@endors/widgets";

mount(document.getElementById("wall"), { embedId: "your-embedding-id" });

The widget loads the same live embed document as the copy-paste snippet, auto-resizes to the content, and updates automatically whenever you change the wall in Endors. No API key in frontend code — embedding ids are public by design.

Smart embed — matched walls per visitor

One embed, many pages: pass a free-form match context and the wall shows testimonials matched to that context at render time instead of the curated list — no backend, no API key, no extra round-trip. Endors' deterministic proof-matching engine runs server-side when the embed document renders (no LLM interpretation, no credits, ~1s) and picks the strongest matches from the workspace's shareable testimonials, filtered to the embedding's testimonial type. Nothing matches → the curated wall renders; the embed never blanks the host page.

wall.tsx 
// After a form submit — the visitor's own words pick the proof:
import { mount } from "@endors/widgets";

mount(document.getElementById("wall"), {
  embedId: "your-embedding-id",
  match: formData.education + ", " + formData.previousWork,
});

Copy-paste snippet equivalent:

html 
<div data-endors-embed-id="your-embedding-id"
     data-endors-match="studied business at DCU, worked 5 years in retail"></div>
<script src="https://app.endors.io/embed.js" async></script>

For popups and dynamic UIs that know the context only at open time, use a getter: data-endors-match-getter="getVisitorContext" (the named global function is called at mount), and inject the container after page load, then call Endors.mountAll() to mount it. Matched embeds use a shorter CDN cache (60s vs 1h) since the document varies per visitor context.

A complete flow

The endpoints compose into a full automated intake: upload media, resolve or create the client, create the testimonial, and file it.

1. Upload the media

POST /api/spaces/{spaceId}/assets/upload (image) or the video flow → get an assetId.

2. Create the testimonial

POST /api/spaces/{spaceId}/testimonials with asset_id plus client_first_name / client_email — the client is found or created automatically → get testimonialId and shareUrl.

3. Organize and react

PATCH the testimonial into folders, subscribe to testimonial.created to push it downstream, and query it back with proof match when a sales conversation needs it.
