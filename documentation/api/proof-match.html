Proof match

Given a prospect description and/or structured prospect data, returns the strongest relevant proof from the workspace with scored, grounded reasons — the same output as the dashboard's proof-match flow. Built for sales assistants and pre-call prep.

This is a metered AI endpoint: 20 requests/minute per key (see Rate limits).

POST /api/spaces/{spaceId}/proof/match

Deterministic per request: at most one LLM interpretation call and one embedding call, both degrading gracefully. An empty matches array with a coverage object is a normal "no match" result, not an error.

Request body

FieldTypeDescription
description string Free-form prospect description. At least this or one meaningful prospect field is required.
prospect object Structured prospect: industry, subIndustry, businessType, companySize, customerSegment, location, productOrService, gender, revenue ({ value, currency, period }), painPoints, desiredOutcomes, objections, previousAlternatives, notes, customFields.
filters object Hard filters: assetTypes (video, image, text, document, transformation), clientIds, industries, outcomes, hasQuantitativeResult, gender.
eligibility string shareable (default) — only approved, shareable proof; or library for everything.
limit integer Max matches. Defaults to 5, capped at 20.
includeScoreBreakdown boolean Include the per-dimension score breakdown on each match.

Request

bash 
curl -X POST "https://app.endors.io/api/spaces/$SPACE_ID/proof/match" \
  -H "Authorization: Bearer $ENDOR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "description": "UK dental agency doing ~£50k/mo, struggling with CAC",
    "prospect": {
      "industry": "Dental",
      "businessType": "Agency",
      "customerSegment": "B2B",
      "location": "UK",
      "revenue": { "value": 50000, "currency": "GBP", "period": "month" },
      "painPoints": ["high CAC"],
      "desiredOutcomes": ["reduce CAC"]
    },
    "filters": { "assetTypes": ["video"] },
    "limit": 5
  }'

Response

json 
{
  "ok": true,
  "data": {
    "matches": [
      {
        "proofId": "b3f2…",
        "proofType": "text",
        "title": "Sarah Mitchell",
        "client": { "id": "7a1e…", "name": "Sarah Mitchell", "company": "Northwind" },
        "excerpt": "Our dental agency cut CAC from $94 to $61 in six months.",
        "shareUrl": "https://app.endors.io/share/ab12cd34ef",
        "score": 0.82,
        "reasons": [
          { "code": "industry", "label": "Same industry: Dental", "confidence": 1.0 },
          { "code": "objection", "label": "Matches the objection: a previous agency failed", "confidence": 1.0 },
          { "code": "metric", "label": "Verified CAC: $94 to $61", "confidence": 0.9 }
        ]
      }
    ],
    "coverage": { "eligibleAssets": 4, "indexedAssets": 3, "matchedCandidates": 4, "unprocessedAssets": 1 }
  }
}

Matching rules

  • Grounded reasons only. Every reason maps to stored proof metadata, normalized text, or a structured metric — never to private notes or sensitive custom-field values.
  • No guessed values. A missing value is never converted into a guessed one; a conflicting inferred value never overwrites a known explicit one.
  • Gender signals. prospect.gender is a soft signal — a match adds an identity-strength reason ("Same gender: female"), a mismatch adds nothing. filters.gender is a hard filter — only testimonials whose client gender matches (after a synonym layer: woman/female/she → female, man/male/he → male) are returned. The deterministic engine matches only the stored client field; it never infers gender from names or pronouns.

Errors

400 invalid/empty request · 401 unauthenticated · 403 not a member · 500 unexpected internal failure. An empty matches array with coverage is a successful response — design your fallback copy for it.

Tenancy is fixed

spaceId and caller identity are never taken from the body — they come from the path and your key. A response always covers the key's own space.
