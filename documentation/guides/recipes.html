Recipes

Recipes are indexed by the trigger you already have, not by endpoint. Each one is: one trigger + one Endors capability + a few lines of your code. The integration patterns below are tested against the live endpoints; where a recipe touches another product (Stripe, Calendly, Slack), that product's own docs cover its side — ours covers the Endors half.

Recipe 1 — Post-payment ask

Trigger: a successful checkout in your system (Stripe, Paddle, your own billing).
Capability: POST /sessions.
Scenario: the moment a customer pays is the moment they're happiest — ask for the testimonial then.

In your payment webhook handler (server-side — never expose your key in the browser):

js 
// inside your checkout.completed handler
await fetch(`https://app.endors.io/api/spaces/${SPACE_ID}/sessions`, {
  method: "POST",
  headers: {
    Authorization: `Bearer ${process.env.ENDORS_API_KEY}`,
    "Content-Type": "application/json",
    // protects against the double-fired webhook (the classic first-integration bug)
    "Idempotency-Key": `checkout-${event.id}`,
  },
  body: JSON.stringify({
    type: "collection",
    customerName: customer.name,
    email: customer.email,
    source: "stripe-checkout",
    context: "Thanks for upgrading to Pro! Would you share what convinced you?",
    metadata: { stripeCustomerId: customer.id },
  }),
});
// → { ok, data: { id, url, status: "pending", … } }

Then deliver data.url however you already talk to this customer (your receipt email, in-app message, etc.). Endors never sends email on your behalf — the email field is for dedupe + webhook correlation only.

Two behaviors do the worrying for you:

  • Retries are safe. The same Idempotency-Key returns the original response verbatim; a different body with a used key is 409 IDEMPOTENCY_REPLAY_MISMATCH (your bug — don't retry).
  • Double triggers are safe even without idempotency. The same email + source within 7 days returns the existing session with deduplicated: true (HTTP 200) instead of spamming your customer with a second ask. A genuine second ask: force: true or a different source.

Recipe 8 — Pre-call page on autopilot

Trigger: a meeting gets booked (Calendly webhook, CRM deal stage change).
Capability: POST /sessions with type: "precall".
Scenario: your sales team walks into every call with a brief built from your proof library.

js 
await fetch(`https://app.endors.io/api/spaces/${SPACE_ID}/sessions`, {
  method: "POST",
  headers: {
    Authorization: `Bearer ${process.env.ENDORS_API_KEY}`,
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    type: "precall",
    customerName: "Dana Lee",
    email: "dana@example.com",
    templateId: "tpl_your_pre_call_template", // omit for the space default
    context: "Head of Ops at a 40-person logistics company, evaluating after a demo, concerned about onboarding time",
    source: "calendly-booked",
  }),
});

context is required for precall sessions — it's what the pre-call generation works from; the more specific it is, the sharper the brief. Note the two details that make this zero-maintenance: the response is the same { id, url, status } shape as every other session, and precall sessions draw AI credits — an exhausted balance returns 402 AI_CREDITS_EXHAUSTED with a paywall payload rather than a silent failure. Give the generated page's url to the rep (or email it to the customer).

Recipe 9 — Onboarding proof

Trigger: a user reaches the part of your product where a claim needs backing ("companies like yours…").
Capability: POST /proof/match — the grounded, scored, cited proof query.
Scenario: pull the strongest relevant testimonial for this user's situation, with reasons you can defend.

js 
const res = await fetch(`https://app.endors.io/api/spaces/${SPACE_ID}/proof/match`, {
  method: "POST",
  headers: {
    Authorization: `Bearer ${process.env.ENDORS_API_KEY}`,
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    description: "Logistics company, ~40 employees, worried about switching costs",
    filters: { hasQuantitativeResult: true },
    limit: 3,
  }),
});
const { data } = await res.json();
// data.matches[0] → { excerpt, score, reasons: [{ code, label, sourceId }], shareUrl }

Every match carries reasons — machine-checkable citations ("Same industry: Logistics", "Verified onboarding time: 3 weeks → 9 days") pointing at stored metadata, never invented. Render the excerpt with its shareUrl; hide the machinery. An empty matches array is a normal answer, not an error — have a neutral fallback copy for it. AI-tier rate limit: 20 requests/minute per key.

Recipe 19 — Live social-proof badge

Trigger: any page load where social proof helps (signup, pricing, landing).
Capability: GET /proof/stats — one call for live badge numbers (the full response shape is in the sample below).
Scenario: a real, live counter instead of a hardcoded one.

Server-side (or a light edge function), then cache on your side — the endpoint itself serves from a 60-second cache and reports cached: true/false, but your page shouldn't call it per visitor at all:

js 
// fetch at most once a minute, cache the rest
const res = await fetch(`https://app.endors.io/api/spaces/${SPACE_ID}/proof/stats`, {
  headers: { Authorization: `Bearer ${process.env.ENDORS_API_KEY}` },
});
const { data } = await res.json();
// data → { totalTestimonials: 142, avgRating: 4.8, videoCount: 38,
//          imageCount: 21, textCount: 83, documentCount: 0, clientCount: 96 }

Render data.clientCount as "Trusted by 96 companies" and data.totalTestimonials as "— 142 verified stories". avgRating is null when no ratings exist — branch on that.

Recipe 25 — React to completion

Trigger: a customer completes an ask.
Capability: the session.completed webhook + the metadata you stored at creation.
Scenario: the completion is the trigger for your next workflow — unlock a perk, ping Slack, update the CRM.

Create the session with whatever correlation data you need (Recipe 1), then react when it comes back:

js 
app.post("/webhooks/endors", (req, res) => {
  // verify the signature first — see "Verifying webhook signatures"
  if (req.body.event === "session.completed") {
    const { sessionId, source } = req.body;           // top-level context fields
    const { email, metadata, customerName } = req.body.data;  // echoed verbatim

    // metadata is YOUR payload from creation time:
    slack.post(`🎉 ${customerName} (${email}) completed a testimonial — source: ${source}`);
    crm.update(metadata.stripeCustomerId, { testimonial_collected: true });
  }
  res.sendStatus(200); // ack within 10s; process async if slow
});

sessionId and source ride at the top level of every session payload and are also in data. Your handler must return a 2xx within 10 seconds — acknowledge first, process in a queue. Failures retry automatically (immediately, 2s, 8s, 32s, 128s); a 4xx marks the delivery exhausted with no retry.

Sessions pending for too long are recoverable — list sessions filtered by status=pending&createdAfter=… and re-send the url.
